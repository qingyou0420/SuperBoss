# SuperBoss 开发治理护栏设计

> 日期：2026-08-12
> 状态：OWNER 已逐节确认，等待书面复核
> 历史基线：`51cd8491fa593eb3095684d7528ecea6d1dc17de`

## 1. 目的

本设计防止未来开发再次出现以下失衡：

- 将安全威胁模型推到当前产品和部署拓扑之外；
- 为尚不存在或不可达的功能提前建设恢复、兼容和抽象层；
- 在开发或审查过程中自行提高交付标准；
- 在相同代码状态上反复运行全量测试、构建和独立审查；
- 以“更安全”“更完整”“以后可能需要”为理由引入其他未批准工作。

治理对象包括所有人工开发者、AI/Codex、审查者和 CI。规则写入仓库，由 CI
执行；不能只依赖提示词或自觉。

## 2. 非目标

本设计不：

- 追溯阻断历史 216 个提交；
- 立即拆除已实现的可靠性或安全机制；
- 引入 OPA、独立策略服务、审计数据库或治理机器人；
- 用代码行数代替产品判断；
- 降低认证、权限、秘密保护和数据完整性的基本安全底线；
- 要求每个小修复获得 OWNER 人工点击批准。

当前 HEAD 作为历史基线。既有过度设计进入技术债清单，今后按触碰范围逐步收敛。

## 3. 核心原则

1. **审查验证合同，不创造合同。** 审查者不能把建议、Minor 或理论风险自动变成
   阻塞要求。
2. **现实威胁优先。** 安全机制必须绑定现实攻击者、可达入口、受保护资产和具体损害。
3. **产品需求先于未来可能。** 不为尚不存在的接口、角色、租户、平台或部署方式提前建设。
4. **最小变更。** 每个任务只解决一张任务卡中的成功条件。
5. **证据复用。** 相同代码树、任务卡和门禁的绿色证据不得机械重跑。
6. **例外必须窄且过期。** OWNER 批准只覆盖明确范围，并在当前变更合并时失效。
7. **历史债不扩散。** 未触碰的历史问题不阻断无关开发；一旦触碰，必须声明维持、收敛或删除。

## 4. 仓库结构

实施后增加以下最小结构：

```text
.governance/
├── policy.json
├── baseline.json
├── task-card.schema.json
├── tasks/<task-id>.json
└── approvals/<approval-id>.json

scripts/
├── governance_check.py
└── verify_changed.py
```

- 使用 JSON 和 Python 标准库，不新增治理依赖。
- 一个 PR 或候选变更只允许一张活动任务卡。
- `baseline.json` 记录历史基线、已接受技术债和当前规模，不保存重复 diff。
- `policy.json` 保存不可由任务卡自行放宽的规则。
- `approvals/` 只保存窄范围 OWNER 例外，不保存秘密或聊天全文。

## 5. 任务卡

每项非纯机械开发在写生产代码前必须声明：

```json
{
  "task_id": "example-id",
  "level": "L1",
  "problem": "用户可观察的问题",
  "success_criteria": ["SC-1"],
  "allowed_paths": ["web/src/example/**", "web/tests/example.test.ts"],
  "non_goals": ["不新增接口", "不改变认证方式"],
  "threat_model": {
    "assets": [],
    "attackers": [],
    "capabilities": [],
    "entry_points": [],
    "excluded_capabilities": []
  },
  "budgets": {
    "files": 8,
    "production_lines": 250,
    "test_lines": 500,
    "migrations": 0,
    "dependencies": 0,
    "services": 0,
    "routes": 0
  },
  "verification": ["focused", "static"],
  "stop_conditions": ["SC-1 通过", "无未关闭 Critical/Important"]
}
```

实际 schema 可以增加机器字段，但不能加入可被开发者用来无限放宽预算的通配机制。

## 6. 变更分级和默认预算

| 等级 | 典型变更 | 默认预算 | 默认验证 |
|---|---|---|---|
| L0 | 文档、文案、注释 | 5 文件、300 文档行 | 格式、链接、治理检查 |
| L1 | 局部缺陷、单组件行为 | 8 文件、250 生产行、500 测试行 | focused + 静态检查 |
| L2 | 已批准的新功能 | 20 文件、700 生产行、1000 测试行 | focused + affected suite |
| L3 | 认证、权限、数据库、外部 I/O、部署边界 | 不自动放行 | OWNER 批准的专项门禁 |

预算是强制停下来重新确认的阈值，不是追求更多代码的目标。超预算时只能：

1. 删除非必要设计；
2. 拆分任务；
3. 取得窄范围 OWNER 批准。

以下变更自动提升为 L3：

- 新认证来源、Token 来源、CSRF 例外、权限角色或信任区域；
- 新表、迁移、外键级联、数据库触发器或长期后台任务；
- 新依赖、容器、服务、公开路由、网络出口或监听端口；
- 新的秘密存储位置或长期本地状态；
- 外部存储、支付、账号、权限或不可逆数据的 exactly-once 协议；
- 修改生产回滚、备份恢复或部署信任边界。

## 7. 威胁模型护栏

安全 finding 只有在同时给出以下证据时才能阻断：

1. 当前系统中的受保护资产；
2. 现实攻击者身份；
3. 攻击者在当前拓扑中已经拥有的能力；
4. 可达的入口和完整调用路径；
5. 可复现的影响；
6. 修复不超出任务卡范围，或已获得范围变更批准。

例如，恶意服务器返回预签名 URL 属于现实边界；同一 SPA 中任意代码可替换全部
JavaScript intrinsic 已等价于任意同域代码执行，默认属于排除能力，不能据此继续重写
HTTP 栈。

审查结论固定分为：

- **合同违背**：可阻断；
- **当前威胁模型内的可复现缺陷**：可阻断；
- **防御性建议**：只进入技术债；
- **理论或未来场景**：标记 out-of-scope。

安全建议不能因为措辞包含“secret”“SSRF”“race”或“fail closed”就自动获得高等级。

## 8. 防止其他过度开发

默认禁止：

- 为尚不存在的功能建设恢复、兼容、删除或迁移协议；
- 只有一个使用方却创建通用框架或扩展点；
- 无基准数据进行性能优化；
- 为未批准的平台、租户、云服务或部署方式提前抽象；
- 将第三方库私有执行顺序冻结为产品合同；
- 穷举所有理论线程调度、Unicode 变体、深层 JSON 或控制台故障；
- 增加未被成功条件消费的接口、页面、配置、状态或日志；
- 创建多份相互冲突的需求、设计和计划基线；
- 保存每轮完整 diff、重复报告或重复证据副本；
- 在预 1.0 内为未承诺兼容的内部实现长期维护兼容层。

以下不视为过度开发：

- 认证、授权、秘密和项目隔离的基本正确性；
- 可导致不可恢复数据损坏或越权的真实缺陷；
- 外部副作用发生后的必要幂等和响应丢失恢复；
- 冻结需求明确要求的 ClamAV 隔离、CLEAN-only 下载和设备最小权限；
- 与实际修改直接相关的迁移、部署或备份验证。

## 9. CI 治理门禁

`governance_check.py` 必须在测试和构建之前运行，并验证：

1. 恰好一张活动任务卡；
2. 任务卡 base commit 是当前变更的祖先；
3. 修改路径都属于 `allowed_paths`；
4. 实际文件数和行数未超预算；
5. 依赖、迁移、路由、服务和容器变化与声明一致；
6. 触发 L3 的路径或语义变化具备有效 OWNER approval；
7. 测试变化能够映射到成功条件、已复现缺陷或批准风险；
8. 没有未声明的生成物、完整 diff 快照或重复报告；
9. 验证计划符合变更分类；
10. 例外未过期，且没有被当作全局先例。

机器检查首先采用可维护的路径和清单比较，不建设静态分析平台。只有实际逃逸案例证明
路径规则不足时，才增加更精确的解析。

## 10. OWNER 批准和分支保护

`.governance/policy.json`、`.governance/baseline.json` 和 `approvals/` 由
`CODEOWNERS` 指向 OWNER。代码托管平台的分支保护要求 OWNER 批准这些文件的变更；
开发者或 AI 可以提出记录，不能自行批准。

符合默认策略和预算的 L0–L2 任务卡不要求 OWNER 逐项批准。L3 任务卡、任何超预算任务卡，
以及试图放宽策略的任务卡必须引用有效 approval，并由 OWNER 审核对应例外。

批准记录必须包含：

- 允许突破的具体规则或数值；
- 原因和用户收益；
- 精确路径；
- 对应 task ID；
- 失效条件，默认当前 PR 合并即失效。

“后续按推荐推进”不构成永久安全边界、预算或交付标准放权。

没有远程仓库或分支保护时，本地检查只能标记“等待 OWNER 审批”，不能把开发者写入的
approval 文件视为独立批准。

## 11. 分层验证

所有验证通过 `verify_changed.py` 选择：

- L0：格式、链接和治理文件；
- L1：直接相关测试和对应 lint/typecheck；
- L2：focused 后运行 affected subsystem；
- L3：只运行与声明边界相关的专项门禁；
- 候选合并：在冻结 commit 上完整 backend、web、connector 各一次。

触发示例：

- 迁移或 ORM schema 变化：Alembic、真实 PostgreSQL、相关 schema tests；
- Docker/Nginx 变化：compose config、build、smoke；
- connector 打包变化：Windows build；
- import-time wiring 变化：no-network import；
- 外部 I/O 状态机变化：故障注入、幂等和残留检查；
- 普通页面变化：相关 Vitest、lint、typecheck，不运行后端全量。

## 12. 防止重复验证

验证证据键为：

```text
代码树 SHA + 任务卡 SHA + 门禁名称
```

相同证据键已经通过时，工具报告已有证据，不重新执行。允许重跑的情况只有：

- 上次属于环境或工具故障；
- 代码树或任务卡已变化；
- 正在调查 flaky test；
- OWNER 批准并记录理由。

CI 对同一分支取消旧流水线。Reviewer 复用实现者的绿色门禁，只运行独立静态审查、
affected suite 和最多三个针对声明风险的反证探针。

失败后的顺序是：失败节点 → focused 修复 → affected suite → 新候选唯一一次全量。

默认时间预算：L1 五分钟、L2 十五分钟、L3 专项三十分钟。超时优先拆分矩阵，不自动
增加重跑次数。

## 13. 测试选择

永久测试优先级：

1. 用户可观察行为；
2. 权限、秘密和数据损坏；
3. 已实际复现的故障；
4. 稳定公共协议。

默认不锁定私有函数形状、所有约束名称、第三方内部执行顺序和所有理论调度组合。

测试增量超过生产增量两倍时，CI 给出警告并要求任务卡解释；它不是绝对失败条件，避免
迫使开发者减少必要的安全测试。实际测试行数仍受任务卡绝对预算约束。

## 14. 审查停止条件

任务在以下条件同时满足时必须停止扩张：

- 所有成功条件已通过；
- 没有未关闭的 Critical 或 Important；
- 一轮实现者自审和一轮独立审查完成；
- 候选验证满足计划。

第二轮修复审查只验证原阻塞项和受影响回归。第三轮审查默认被 CI 阻断，除非存在新的
当前威胁模型内可复现证据并获得 OWNER 批准。

Minor 不自动成为当前任务；新发现若不阻止当前安全交付，则进入 backlog。

## 15. 报告和提交

每项任务最多保留：

- 一份活动任务卡；
- 一份必要设计；
- 一份必要实施计划；
- 一份最终结果摘要。

不在仓库或 ignored 工作区长期保存多轮完整 diff。审查上下文由 PR 平台保存。交付前将
红绿过程整理成少量逻辑提交；不要求为每个测试例或格式修改永久保留独立 commit。

## 16. 指标和阈值

CI 每次只输出：

- 实际/批准文件数；
- 生产和测试行数增量；
- 新接口、表、迁移、依赖、服务和后台任务数；
- 威胁模型变化数；
- affected/full 运行次数与耗时；
- 审查轮数；
- 新增 backlog 数。

默认触发：

- 单文件修改后超过 800 行：要求拆分说明；
- 测试增量超过生产增量两倍：要求解释；
- 第三轮审查：阻断；
- 相同候选第二次全量：阻断；
- 新依赖、服务、认证来源、路由或数据库表：无批准失败；
- 未被成功条件消费的新增接口、配置或状态：失败。

这些指标用于要求解释和控制增量，不对历史基线追责，也不能作为鼓励写满预算的 KPI。

## 17. 当前历史技术债

`baseline.json` 初始记录：

- 浏览器 Bearer 备用认证通道；
- Connector global-only DNS 与 pinned transport；
- 当前产品不可达的 File/Project 删除恢复协议；
- JWT secret 熵启发式；
- pairing output exactly-once marker；
- 超大服务和测试文件；
- 重复测试矩阵；
- 多轮 ignored reports 和 diff 快照。

这些项目不阻断无关工作。触碰相关模块时，任务卡必须声明“维持、收敛或删除”。

## 18. 实施顺序

1. 建立 policy、baseline、schema 和最小任务卡模板；
2. 实现路径、预算和 L3 触发检查；
3. 实现 changed-path 验证选择；
4. 接入 CI、CODEOWNERS 和分支保护；
5. 加入证据键、防重复和审查轮次检查；
6. 用一个纯文档任务和一个 L1 修复演练；
7. 再决定是否需要更精确的语义分析。

实施本身必须作为一个受本设计约束的 L2 任务，不得借治理之名引入独立平台。

## 19. 成功标准

治理护栏完成后必须证明：

- 未声明路径、预算超限和新边界会稳定失败；
- 有效、窄范围 OWNER approval 只放行对应例外；
- 当前历史基线不会阻断无关 L0/L1 任务；
- 普通页面修改不会运行后端、Connector 或 Docker 全量；
- 同一候选的第二次全量会被拒绝或复用已有证据；
- reviewer 无法用 Minor、建议或 out-of-scope 理论问题抬高合同；
- 治理工具自身不需要新服务或第三方运行依赖。
