# SuperBoss 迭代方案：诊断与瘦身计划

日期：2026-08-24。适用范围：整仓（server / web / 连接器 / 测试 / 治理 / 文档 / 部署）。

## 一、结论摘要

本仓库此前由 Codex 以"任务卡 + 预算 + 门禁"的重流程方式开发，产出质量参差：**核心业务能力（隔离扫描、认证、连接器提交）是健全的，但包裹它们的工程外壳严重超配**——约 1.57 万行产品代码背着约 3.5 万行测试代码；236 个提交中 76 个是 fix，其中约一半的历史都在修补文件上传这一个子系统。方向建议：**不加新功能，先做三件事——拆除自研治理系统、修正确性 bug 并打通操作路径、然后分层删减**。预计可删除约 4000 行产品代码与约 2 万行测试代码而不损失任何实际功能。

各部分体量（行数，含证据基线）：

| 区域 | 产品代码 | 测试代码 | 备注 |
|---|---|---|---|
| server/src | 8404 | 22124 | 测试/产品比 2.6:1 |
| web/src | 4653 | 5103 | 另有 tests/e2e 1068 行、tests/compose 852 行 |
| 连接器 src | 2629 | 6998 | 测试/产品比 2.7:1 |
| 治理脚本 scripts/ | 649 | 946（在 server/tests/unit/governance） | 纯流程机器 |
| docs/superpowers | — | — | 3648 行一次性 AI 过程文档 |

## 二、主要问题与证据

### P0：正确性 bug（不删代码也必须修）

1. **上传成功却返回 503**。`complete_upload` 提交成功后由请求内联投递 outbox；若 30s 的进程内 reconciler（`server/src/superboss/main.py` L38-49）或 60s 的 beat 任务已抢先认领租约，`deliver_completion` 返回 False，客户端收到 `503 FILE_DELIVERY_PENDING`（`server/src/superboss/modules/files/router.py` L159-166；`imports/router.py` L99-105 同型）。
2. **数据库触发器与 Python 清理记录的去重键算法不一致**。触发器用 `lpad(md5(...),64,'0')`（`server/migrations/versions/0015_discover_unbound_multipart.py` L67/77/89），Python 用 sha256（`modules/files/service.py` L381-383、L724-748），唯一约束 `uq_file_storage_cleanup_operation_dedupe` 对两个写入方互不去重。
3. **扫描期间持有行锁最长 600 秒**。`scan_file` 在单事务内锁 File 行并完成下载+ClamAV 扫描（`files/service.py` L109-150），期间任何 `complete_upload` 重放或 `presign_download` 都会阻塞分钟级。
4. **扫描失败的对象永不清理**。`HASH_MISMATCH`/`SCAN_FAILED` 置 FAILED 后不落 `DELETE_OBJECT` 清理行，MinIO 对象永久残留。
5. **登录页对"登录"套用"新密码"策略**。`web/src/api/auth.ts` L63-77 在登录前本地校验 12-128 位密码与用户名字符集，不满足则直接显示"用户名或密码错误"，请求根本没发出。
6. **前端状态判断依赖服务端 message 原文逐字匹配**。`web/src/api/files.ts` L202-229 要求 `message === 'File did not pass security scanning'` 才认定 INFECTED，服务端改一个词，染毒文件将永远显示"仍在扫描中"；`projects.ts` 的冲突判断同病。
7. **100MB 上限对用户不可见**。超限/空文件/MIME 不合法一律显示"文件上传失败，请稍后重试"（`web/src/components/files/MultipartUploader.vue` + `uploads/multipart.ts`），重试永远不会成功。
8. **import 审计 event_key 设计缺陷**。`imports/service.py` L976-981 的 uuid5 键只编码 (action, job, status) 不含 result_code，同状态不同结果码重入会触发唯一索引冲突并回滚整个提交事务。
9. **dev 栈五个端口绑 0.0.0.0 且凭据弱**：Postgres superboss/superboss:5432、Redis 无密码:6379、MinIO 及控制台:9000/9001、API 明文:8000（`docker-compose.dev.yml`），笔记本接入任何局域网即暴露。prod 的 `"443:443"`（`docker-compose.yml` L38）也与文档声称的 127.0.0.1 绑定矛盾。
10. **README 的主线操作不可执行**：dev 栈没有 web/nginx 服务，`https://app.localhost/login` 无法访问；生产栈需要的自签证书、allowlist、hosts 配置全仓库没有任何文档（grep openssl/mkcert 零命中）。另外 `.env.example` 中 25 个变量有 11 个是死变量（compose 里写死了字面量，改了不生效）。

### P1：自研治理系统是最大的负资产

`scripts/governance_check.py`（412 行）+ `verify_changed.py`（237 行）+ `.governance/`（政策/基线/任务卡 JSON）+ 946 行专属测试 + `.github/workflows/governance.yml`，合计约 1700 行流程机器。具体故障模式：

- **任何变更都要先手写一张含 threat_model、12 维预算、成功判据的 JSON 任务卡**，且全仓只允许一张 active 卡（`governance_check.py` L118-120），否则所有 CI 失败。
- **非 draft 的 PR 按现状必挂**：candidate 模式要求卡上 `candidate:true` 且声明 backend-full/web-full/connector-full 三个闸门（`verify_changed.py` L60-73），当前 active 卡（`.governance/tasks/connector-cloud-update.json`）两者皆不满足。
- **CI 从不执行 `npm ci`**（governance.yml 全部步骤可查），所以一旦触发任何 web 闸门（web/ 目录被改动即触发）必然以"vitest 不存在"失败。
- **闸门输出全部丢进 DEVNULL**（`verify_changed.py` L118-120），CI 上只能看到 FAILED 无任何日志，不可排障。
- **12 个预算维度里 8 个从不度量**（migrations/dependencies/services/containers/routes/auth_sources/persistent_state/network_boundaries 只校验"声明了"，`check()` 只比较 4 个行数/文件数维度）——纯剧场。
- **L3 触发按文件名关键词**：路径含 "auth"、"state"、"network" 即要求审批（L263-291），例如改 `web/src/stores/auth.ts` 就触发 L3，而 `.governance/approvals/` 目录根本不存在。
- **证据缓存的 CI cache key 是 `governance-evidence-${{ github.sha }}`**，每个提交必然 miss，缓存机制形同虚设。
- 落地本文档本身就被迫演示了这套流程：必须改两张任务卡、且文档不得超过 300 行（L2 documentation_lines 预算）。

### P2：后端过度工程（server/src 8404 行，可删约一半）

- **文件生命周期：5 张表 21 个状态值管一次上传**（`files.state` 6 + `file_upload_lifecycle` 4+5 + outbox 3 + cleanup 3，`modules/files/models.py` L30-302），其中 `VERIFIED` 全仓无赋值点（仅存在于 CHECK 约束 L136-139）、`SCANNING` 在事务内 flush 从不可见、`CANCEL_REQUESTED` 只有 plpgsql 触发器写入。**18 个迁移中 11 个（0005-0015）是对该子系统的修补**，0013 的 upgrade() 是空的。
- **同一 reconcile 逻辑三处并发运行**：FastAPI lifespan 30s 循环、Celery beat 60s 任务、请求内 `_best_effort_cleanup`——租约字段主要在保护这三个冗余副本互不踩踏。生产 compose 因此跑 api + 两个专属 worker + beat 四个 Python 进程，服务单人。
- **幂等实现了四套**（uploads 唯一约束、`import_idempotency_claims` 表、派生子键、audit event_key），**审计重放校验三处复制**（`audit/service.py` L58-74、`devices/service.py` L154-171、`files/service.py` L784-802）。
- **两套完整 token 栈**：DeviceSession 与 AuthSession 各自实现轮换刷新、jti 绑定、过期交叉校验，服务对象是一位 OWNER 和一台连接器设备。
- **41 个自定义异常类服务 32 条路由**；users/projects/auth 有纯透传 Repository 层而复杂模块反而没有；死代码：`FileStorageFailureError`、`UserRepository.by_username/disable/change_role/delete`、`ProtectedOwnerError`、`ProjectStatus.ARCHIVED`、未使用的 `cryptography` 依赖。
- **审计写放大且无处可读**：每个设备请求写一条 `device.use`、OWNER 每次列用户写一条 `user.list`，但审计模块没有 router，只能进 psql 看。
- 配置校验偏执：JWT 密钥做 base64url 规范化往返 + **字节周期性分析**（`core/config.py` L93-109），S3 端点做完整 RFC 主机名逐标签校验——使用者是在自己机器上填配置的 OWNER 本人。

### P3：前端过度工程与测试剧场

- `web/src/api/http.ts` 564 行在防御"敌意调用方"（walk 属性描述符、拒绝 getter、深冻结、2 万节点 JSON 预算），而治理任务卡自己声明排除了同源 JS 攻击者（`.governance/tasks/development-governance-guardrails.json` excluded_capabilities）。约 60 行 axios 封装可覆盖全部真实需求（baseURL、CSRF 头、401 刷新单飞）。
- 6 个 API 模块复制了 7 份 `isRecord/exactKeys/safeText` 校验器并做**精确键集匹配**：后端任何新增响应字段都会让整个 UI 报"服务暂时不可用"。
- 上传管线 835 行：全文件读入内存计算 sha256 后，PUT 前对同一不可变 Blob **再哈希一遍自检**，每次哈希新建一个 Worker——100MB 上传创建 14 个 Worker、做约 200MB 哈希，没有进度条。
- 测试剧场：`http-facade.test.ts`（697 行）测试"敌意 `Object.prototype.toJSON`"等被排除的威胁；`tests/e2e/contracts/` 5 个 spec 大多是 **readFileSync 读源码做 grep 断言**；`tests/compose/test_production_contract.py`（422 行）把 compose YAML 逐字转写成 Python 断言（连镜像 digest 后面的注释格式都用正则锁死）。**而 tests/e2e 与 tests/compose 在 CI 里从不运行**（governance.yml 的 `e2e-contract` 闸门实际跑的是 `server/tests/unit/test_deployment_contract.py`，`compose` 闸门只跑 `docker compose config`）。
- 前端死代码：`@element-plus/icons-vue` 零引用、`fileErrorMessage` 无调用方且忽略入参、`UsersPage.vue` 为测试注入而留的 `userApi` prop、`bootstrap(force)` 的 force 从未传入。

### P4：连接器与文档

- 连接器为"从自己机器传文件到自己服务器"实现了 `pinned.py` 238 行自研 httpcore 网络后端（DNS 钉扎）、`outbox.py` 505 行带 fsync/文件锁/替换标记/配对完成标记的崩溃恢复协议、6998 行测试。工作可靠但维护成本与收益完全不成比例；更新器（updater.py）与发布流水线（connector-release.yml）质量尚可，保留。
- `docs/superpowers/` 9 个文件 3648 行是一次性 AI 计划文档，其中 m1-foundation 计划仍承诺不存在的 WeCom OAuth，两处声称"只发布 127.0.0.1:443"与 compose 实况矛盾。`docs/01-需求定稿.md` 写 BullMQ/pgvector/deploy.sh，实际是 Celery/无 pgvector/无此脚本；`02-架构设计.md` 的服务清单含不存在的 agent，漏掉 clamav/worker/beat。dev 与 prod compose 还存在数据库大版本漂移（Postgres 17 vs 18、Redis 7.4 vs 8、ClamAV 1.4 浮动 tag vs 1.5.3 digest）。

## 三、方向建议

以"**一位 OWNER 在一台 Windows 机器上可靠使用的内部工作台**"为唯一准绳做减法。判断标准：每一层机制，若其防御的故障在单机 Docker + 本地 MinIO 环境下十年遇不到一次，就删。先拆治理（它阻塞其余一切工作），再修 bug 与操作路径（让系统真正可用），再删架构赘肉（让后续开发提速），不在干净地基出现前开发任何 M2 功能。

## 四、分阶段计划

### 阶段 0：拆除治理系统，换常规 CI（先做，半天级）

**删**：`scripts/governance_check.py`、`scripts/verify_changed.py`、`.governance/` 整目录、`server/tests/unit/governance/`、`.github/workflows/governance.yml`、`docs/runbooks/development-governance.md`（其 L13-14 还硬编码了 `C:\Users\Administrator\...` 的机器路径）。
**建**：一个朴素的 `ci.yml`——server: `uv run ruff check && uv run pytest tests/unit tests/api`；web: `npm ci && npm run lint && npm run typecheck && npm run test -- --run`；connector: `uv run pytest`；输出直接打到 CI 日志。
**归档**：`docs/superpowers/` 整体移入 `docs/archive/`（或直接删除 plans、保留 specs 作 ADR）。
**完成标志**：任意改动一个文件的 PR（draft 或非 draft）CI 均为绿或给出真实测试失败日志；仓库不再存在任务卡概念。

### 阶段 1：修 P0 + 打通操作路径（与阶段 0 可并行）

**修**：上文 P0 的 1-8 全部；其中 1 的正解是"完成即入队扫描，砍掉 outbox 投递"可留到阶段 2，此阶段先把 `deliver_completion` 遇租约占用时按成功返回。
**加固部署**：dev compose 所有端口映射改 `127.0.0.1:`；prod 443 同理；dev/prod 的 Postgres/Redis/ClamAV 版本对齐；`.env.example` 删除 11 个死变量；nginx healthcheck 改为探测 nginx 自身。
**补文档**：写一篇《本机 HTTPS 部署》runbook（自签证书生成、allowlist 编写、hosts 映射），使 README 的 `https://app.localhost` 从克隆仓库开始可走通。
**完成标志**：按 README + 新 runbook 从零到登录成功全程无需口口相传的知识；用短密码登录能看到真实错误；上传超限文件能看到"超过 100MB"；EICAR 文件下载显示"染毒"而非"扫描中"。

### 阶段 2：后端瘦身（核心工程量所在）

**删**：`FileLifecycleOutbox`/`FileStorageCleanup`/`FileUploadLifecycle` 三表、plpgsql 触发器、`deliver_*`/`reconcile_cleanup` 约 700 行，代之以"完成→置 QUARANTINED→直接入队扫描"+ 每小时一个 janitor 任务清理超 24h 的 multipart 与孤儿对象（MinIO 生命周期策略可承担一部分）；`ImportIdempotencyClaim` 表（唯一约束已提供同等保证）；beat + maintenance 队列 + 专属 worker（收敛为一个 worker 进程，或全部改用 FastAPI 后台任务）；`device.use`/`user.list` 审计写入；死代码清单（P2 末段）。
**并**：Upload 并入 File；DeviceSession 与 AuthSession 合并为带 kind 字段的单会话表；三份审计重放校验收敛为一处；41 个异常收敛到 10 个以内；透传 Repository 并入 service。
**迁移**：新增一个 squash 迁移作为新基线（单人部署可直接重建库，18 个历史迁移随之退役）。
**完成标志**：`server/src` 降到约 4500 行以下；迁移目录只剩基线 + 新增；`docker compose ps` 中 Python 进程 ≤2（api + 1 worker）；上传-扫描-下载全链路 e2e 通过；不再存在任何全仓无赋值点的状态值（以 grep 验收）。

### 阶段 3：前端与测试重整

**前端**：`http.ts` 重写为约 60-100 行 axios 封装（保留 401 刷新单飞与 CSRF）；6 个 API 模块的校验器换成宽松的 code 匹配（禁止匹配 message 原文、禁止精确键集）；上传管线去掉二次哈希与 Worker-per-hash，复用单 Worker 或主线程 crypto.subtle，IndexedDB 断点续传可整体移除；补上传进度条；错误信息至少展示 status + request_id；`/` 重定向到 `/owner` 而非 `/health`；去掉 App.vue 重复页头。
**测试**：删 `tests/e2e/contracts/`（保留 download-boundary 中两个真行为测试）、`tests/compose/test_smoke_contract.py`、`test_runbook_postgres_contract.py`，`test_production_contract.py` 只留"仅 443 发布 + digest 钉扎"两条；删 `http-facade.test.ts`/`http-delete.test.ts`，`http.test.ts` 留约 150 行行为测试；6 个 `auth-*.test.ts` 合并为 2 个；server 侧删除文本断言型元测试（`test_deployment_contract.py`、`test_local_auth_runtime_removal.py`）与故障注入排列组合（约 15 个 ad-hoc storage 假件），目标 server 测试约 4000 行。**保留并入 CI**：4 个 live e2e spec（owner-login-project / file-quarantine / device-import / staff-denial）是全仓价值最高的测试，至少作为发布前手动闸门写入 runbook。
**完成标志**：全仓测试/产品行数比 ≤1.2:1；改动 compose 或 nginx 无需同步改任何测试文件即可过 CI；后端响应新增字段不再导致 UI 报错。

### 阶段 4（可选）：连接器简化与后续开发

评估删除 `pinned.py`（改用 httpx 默认传输 + 证书校验）与 outbox 标记协议简化（保留幂等键与断点续传核心）；此后才开始 M2 文档版本功能。此阶段收益递减，可视阶段 2/3 后的实际维护痛感决定是否执行。

## 五、明确保留的部分（不要动）

隔离扫描核心状态机（UPLOADING→QUARANTINED→CLEAN/INFECTED/FAILED）与 `ClamAVScanner`；Argon2id 密码处理、登录锁定、一次性刷新轮换、CSRF 双提交中间件；prod compose 的 digest 钉扎、零默认密钥、最小端口暴露；两个 Dockerfile 的非 root 多阶段构建；testcontainers 真库测试方法论（保留方法、缩减数量）；连接器 updater 与 connector-release.yml；`manage_local_owner.py` / `seed_acceptance.py`；6 篇 runbook（按阶段 1 修正后）。

## 六、关于本 PR

为在现行治理约束下合规落地本文档：将 `connector-cloud-update` 任务卡置为 complete，新增 L0/L2 级文档任务卡，并将本文控制在 300 行文档预算内——这一过程本身即第二节 P1 所述摩擦的实证。阶段 0 执行后，此类仪式不再需要。
